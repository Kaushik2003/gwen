# Integrations

Everything that talks to something outside the daemon process: desktop notifications and phone
push (v1), Google Calendar, the LLM adapter, and the sync hub (v3). Every integration is optional
and fails soft — see [02-architecture.md](02-architecture.md#failure-and-degradation).

## Credentials

Secrets live in `~/.local/share/gwen/credentials/`, directory mode `0700`, every file mode `0600`.
Never in `config.toml`, never in the database, never in logs.

| File | Contents | Written by |
|---|---|---|
| `ntfy_token` | Optional ntfy access token, one line | `gwen setup phone` |
| `google_client.json` | OAuth client JSON downloaded from Google Cloud Console | `gwen setup calendar` |
| `google_token.json` | `oauth2.Token` as JSON, including the refresh token | daemon, after the OAuth callback |
| `llm_api_key` | Provider API key, one line | `gwen setup llm`, GUI settings |
| `sync_token` | Hub bearer token, one line — on the hub and on each client | `gwen setup sync` |

Files are read at the moment of use, not cached, so replacing one takes effect without a restart.
Writes are atomic (temp file, `fsync`, rename). A missing file makes that feature `unavailable`
with a message naming the setup command.

## Notifications

v1, W4. `internal/notify` has a `Dispatcher` that receives a `Notification{Kind, Title, Body,
Actions}` from the loop after commit and fans it out to backends concurrently, each with a 10 s
timeout. Neither backend blocks the other or the engine loop.

**Routing.** Desktop receives a nudge when `nudge.desktop` is true. Phone receives it when
`nudge.phone` is true, `ntfy.topic` is non-empty, and the kind is marked for phone in
[05-time-engine.md](05-time-engine.md#nudges).

**Text.** `{soft}`, `{hard}` and `{snooze}` are the configured durations; `{elapsed}` is the break
length so far. Durations render as `45s`, `15m`, `1h 5m`.

| Kind | Title | Body |
|---|---|---|
| `idle` | `Still there?` | `No input for {soft}. It stops counting as work at {hard}.` |
| `break_long` | `On a break for {elapsed}` | `Ready to get back to it?` |
| `break_active` | `You're typing during a break` | `End the break so this counts as work.` |
| `clock_in` | `Ready to start?` | `Clock in to start tracking.` |

From v2, when the `clock_in` nudge fires, the loop replaces its body with the briefing summary
`{p} pending from yesterday · {t} planned today · {r} reminders`, omitting zero-count parts, and
falls back to the v1 body when all three are zero.

| Action id | Label |
|---|---|
| `back` | `I'm back` |
| `break` | `Start break` |
| `snooze` | `Snooze {snooze}` |
| `end_break` | `Back to work` |
| `clock_in` | `Clock in` |

### Desktop backend

`org.freedesktop.Notifications` on the session bus via godbus.

- `Notify` with `app_name = "Gwen"`, `app_icon = "gwen"`, hints `urgency = byte(1)` and
  `desktop-entry = "gwen"`.
- `replaces_id` is the id last returned for the same kind, so repeats replace rather than stack.
- `expire_timeout = 0` (persistent) for `idle` and `break_long`; `-1` for the others.
- Actions are sent as `[id, label, ...]`, plus `"default"` mapped to the kind's first action, only
  if `GetCapabilities` includes `"actions"`.
- `ActionInvoked` signals are delivered on `Actions() <-chan ActionEvent{Kind, Action}`, which the
  loop maps to engine inputs per [05-time-engine.md](05-time-engine.md#nudges).
- `Withdraw(kind)` calls `CloseNotification` with the tracked id, if any.
- If the bus or the service is absent at startup, the backend logs `Warn` and becomes a no-op.

### Phone backend (ntfy)

The phone runs the free ntfy app (Android: Play Store or F-Droid; iOS: App Store) subscribed to the
topic. Phone notifications carry no action buttons — the phone cannot reach the daemon socket.

- `POST {ntfy.server}/{ntfy.topic}` with the body as plain text and headers `Title`, `Priority: 4`,
  and `Tags` (`hourglass_flowing_sand` for `idle`, `coffee` for `break_long`).
- `Authorization: Bearer <token>` when `credentials/ntfy_token` exists.
- On a network error or a 5xx, retry once against `ntfy.fallback_server` when it is non-empty. A 4xx
  is not retried. Every failure is logged at `Warn` without the topic.
- `ntfy.topic` is generated by `config.NewTopic()`: `"gwen-"` + 24 lowercase base32 characters from
  `crypto/rand`. The topic is the only thing protecting the channel on a public server, which is why
  it is redacted in logs.

Self-hosting ntfy on the Raspberry Pi is covered in [09-packaging.md](09-packaging.md#raspberry-pi).

## Google Calendar

v3, W12. `internal/gcal`, using `google.golang.org/api/calendar/v3` and `golang.org/x/oauth2`.
Active only when `calendar.enabled` is true and both Google credential files exist.

### One-time setup (by the user)

Google requires every app to have its own OAuth client, so the user creates one. `gwen setup
calendar` prints these steps and then copies the downloaded file into place:

1. Create a project in Google Cloud Console and enable the Google Calendar API.
2. Configure the OAuth consent screen as External, add yourself as a test user, then **publish the
   app to production**. Unverified is fine for personal use; in testing mode Google expires refresh
   tokens after 7 days.
3. Create an OAuth client of type **Desktop app** and download its JSON.
4. Run `gwen setup calendar --client-file <path>`, then connect from the GUI or `gwen cal connect`.

### Authorization

`POST /v1/calendar/auth/start`: the daemon listens on `127.0.0.1:0`, builds an authorization URL
with PKCE (S256), a random `state`, `access_type=offline`, `prompt=consent`, and redirect
`http://127.0.0.1:<port>/callback`, and returns it. The client opens it in a browser. The listener
lives for 5 minutes; on a valid callback it exchanges the code, writes `google_token.json`, closes,
and emits `integration_changed`.

Scopes, and nothing broader:

- `https://www.googleapis.com/auth/calendar.app.created` — manage the calendar Gwen creates.
- `https://www.googleapis.com/auth/calendar.freebusy` — read busy times from other calendars.

### Sync cycle

Runs every 10 minutes, 30 s after the last `plan_changed` (debounced), and on
`POST /v1/calendar/sync`. Steps, in order:

1. **Ensure the calendar.** If `local_state.gcal_calendar_id` is missing, or the calendar returns
   404, create a calendar with summary `calendar.name` and the local IANA zone, store its id, and
   clear `gcal_links` and `gcal_sync_token`.
2. **Pull.** `events.list` on that calendar with `showDeleted=true` and the stored sync token (full
   list when there is none; on `410 Gone`, clear the token and do a full list). For each event whose
   `extendedProperties.private.gwen_id` names a linked plan item:
   - Cancelled → set the item `skipped` if it was `planned`; delete the link.
   - Start or end differs from the item → if the event's `updated` is later than the item's
     `updated_at`, set `start_at`, `planned_minutes`, `day` (the day of the new start), and
     `pinned = 1`. Otherwise leave the item; step 3 overwrites the event.
   - Events without `gwen_id` are ignored. Store `nextSyncToken`.
3. **Push.** The desired event set is every live plan item with `day` from today to today + 13,
   status `planned` or `done`, and non-null `start_at`. Each event has summary = task title
   (prefixed with `✓` and a space when done), start `start_at`, end `start_at + planned_minutes`, description
   `Planned by Gwen`, `extendedProperties.private.gwen_id = <plan item id>`, `transparency =
   opaque`, and `reminders.useDefault = false`. Insert when unlinked; patch when the item's
   `updated_at` is after the link's `synced_at`; delete the event and the link when the item left
   the desired set. Update `etag` and `synced_at` on every write.
4. **Busy.** `freebusy.query` for `calendar.busy_calendars` over `[today 00:00, today + 14 days)`.
   Replace all `calendar_busy` rows in that range; `event_id` is `"<start_at>-<end_at>"`.

Busy times affect only subsequent plan generation ([06-planner.md](06-planner.md#capacity)); a
sync never regenerates a plan by itself. Failures set `last_error`, log `Warn`, and back off
exponentially from 1 minute to 1 hour; a success resets the backoff.

## LLM adapter

v3, W13. `internal/llm`. Optional enrichment with exactly two jobs: propose a task breakdown for a
goal, and write a weekly retrospective. It never schedules, never writes without user acceptance,
and the deterministic planner remains authoritative.

```go
type Planner interface {
    Breakdown(ctx context.Context, req BreakdownRequest) (BreakdownOutput, error)
    Retro(ctx context.Context, req RetroRequest) (RetroOutput, error)
    Name() string
}
```

### Providers

Plain `net/http`; no SDKs. One attempt per request, bounded by `llm.timeout`.

| `llm.provider` | Request |
|---|---|
| `none` | No adapter; the endpoints return `unavailable`. |
| `anthropic` | `POST https://api.anthropic.com/v1/messages`, headers `x-api-key` and `anthropic-version: 2023-06-01`, `model` = `llm.model`, `max_tokens: 4096`. |
| `openai_compatible` | `POST {llm.endpoint}/chat/completions`, `Authorization: Bearer <key>` only if `llm_api_key` exists (Ollama needs none), `response_format: {"type": "json_object"}`. |

Prompts are constants in `internal/llm/prompts.go`. Each instructs the model to reply with a single
JSON object matching the output schema below, and includes that schema verbatim.

### Breakdown

**Sent:** the goal's `title`, `kind`, `unit`, `target_quantity`, `minutes_per_unit`, `start_day`,
`due_day`; the titles of live tasks already linked to the goal; the user's `instructions`; today's
date. Nothing else.

**Output** (`llm_runs.output` when `status = "ok"`):

```json
{"tasks": [{"title": "Arrays: two pointers set", "notes": "", "estimate_minutes": 90, "due_day": "2026-09-20", "priority": 3, "quantity": 5}]}
```

Validation, strict: 1–50 tasks; `title` 1–200 characters; `estimate_minutes` 5–480; `due_day`
between today and the goal's `due_day`; `priority` 1–4; `quantity` null or positive. Any violation,
bad JSON, timeout, or HTTP error stores `status = "failed"` with `output = {"error": "<reason>"}`.
There is no rules fallback for a breakdown; the client shows the error.

`POST /v1/llm/runs/{id}/accept` creates the tasks at the given `indexes` with `goal_id` and the
goal's `project_id`, in one transaction, and sets the run `accepted`. `reject` sets `rejected`.
`subject_id` is the goal id.

### Retro

**Sent:** for the 7 days from `week_start`, each day's DaySummary, per-project totals, titles of
tasks completed, each active goal's progress, and planned versus done plan minutes.

**Output:** `{"markdown": "<at most 4000 characters>", "generated_by": "llm"}`.

On any failure the adapter instead builds a deterministic summary from the same data — totals,
top three projects, target-met days, goals behind pace — and stores it with
`"generated_by": "rules"` and `status = "ok"`. A retro request therefore always succeeds when the
provider is not `none`. `subject_id` is `week_start`.

## Sync hub

v3, W14. The Raspberry Pi runs `gwend --hub`: the same binary cross-compiled for arm64, with no
activity monitor, engine, or notifier. It serves a network API and a read-only dashboard over its
own database, which uses the same migrations.

**Scope.** Sync supports **one tracking device** plus read-only viewers (the phone browser) and
restore after reinstall. It is not multi-device concurrent tracking: a pulled row whose apply would
violate a constraint (for example a second open work day) is skipped, logged at `Warn`, and counted
as ignored.

**Network.** Plain HTTP on `--listen` (default `:7777`) with `Authorization: Bearer <sync_token>`,
compared in constant time. The hub is meant for the home LAN or a Tailscale network; exposure to the
internet must go through a TLS reverse proxy, which is out of scope for Gwen.

### Hub API

| Method and path | Body or query | Returns |
|---|---|---|
| `GET /sync/v1/health` | — | `{"ok": true, "schema_version": 3}` |
| `POST /sync/v1/push` | `{"device_id", "rows": {"<table>": [row]}}` | `{"applied": n, "ignored": m}` |
| `GET /sync/v1/pull` | `?device_id=&cursor=&limit=1000` | `{"rows": {"<table>": [row]}, "cursor": "<seq>", "more": bool}` |

Rows are the complete column set of the synced tables in
[03-data-model.md](03-data-model.md#sync-envelope), keyed by column name. Push applies each row by
last-writer-wins in one transaction with `PRAGMA defer_foreign_keys = ON`, and for every applied row
replaces its `hub_changes` entry, which assigns a new `seq`. Pull returns rows whose `seq` is
greater than `cursor`, excluding rows last written by the requesting `device_id`, in `seq` order.

### Client

`internal/sync`, on the tracking device, every `sync.interval` and on `POST /v1/sync/now`:

1. **Push** rows from each synced table with `updated_at ≥ sync_push_watermark − 5 minutes`, in
   batches of 500. The overlap absorbs clock skew; re-pushing is harmless because LWW is idempotent.
   After all batches succeed, set the watermark to the greatest `updated_at` pushed.
2. **Pull** pages until `more` is false. Apply each page in one transaction with the same LWW rule,
   store the cursor, then emit the matching SSE invalidation events.

Restore after reinstall: `gwen setup sync`, then the first pull with an empty cursor returns the
whole history. The reinstalled device gets a new `device_id`.

### Read-only dashboard

The hub serves the `ui/` build made with `VITE_GWEN_TARGET=hub` at `/`, plus the read-only subset of
the v1 and v2 API from [04-api-contract.md](04-api-contract.md) under the same `/v1` paths: every
`GET` endpoint except `/v1/status`, `/v1/events`, `/v1/config`, and `/v1/briefing`. On the hub,
`GET /v1/plan` returns stored items only and never rolls over or generates. The browser
signs in once by posting the token to `POST /login`, which sets an `HttpOnly`, `SameSite=Strict`
cookie valid for 30 days. The hub build hides every mutating control.
